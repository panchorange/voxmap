# feature-design

実装を始める前に「何を・どんなインタフェースで・どうテストするか」を 1 枚で整理する。
出力はチャット上の確認用テキスト。ファイルには書かない (ADR が必要なら別途 `docs/design/decisions/` へ)。

## いつ起動するか

- 「〜を実装したい」「〜を追加したい」と言われて、変更が src/ や scripts/ に及ぶとき
- 既存の skill / script に大きな変更を加えるとき
- 「どう設計すればいい?」系の相談

単純な typo 修正・docs のみ変更には不要。

## 手順

1. **要件を 3〜5 行で確認**:
   - 「何のために必要か」(ユーザーの目的)
   - 「何を入力・出力とするか」(インタフェースの境界)
   - 「やらないこと」(スコープ外の明示)

2. **インタフェース案を提示**:
   - 関数シグネチャ / CLI コマンド / skill のトリガー条件 を 1 ブロックで
   - 選択肢が複数ある場合は A/B を並べ、トレードオフを 1 行で
   - 深い設計根拠が必要なら `docs/design/decisions/` への ADR を提案する

3. **テスト計画を箇条書きで**:
   - 最低限: happy path の smoke test (エラーなく動く)
   - あれば: 境界値・エラーケース (不正入力、ファイル不在 など)
   - 統合テストが必要かどうかも一言

4. **ユーザーに確認**:
   - 「この方針で進めてよいですか?」と一言聞いてから実装へ
   - 修正依頼があればその場で案を更新する

## やってはいけないこと

- 確認前にコードを書き始めない
- ADR 不要な変更に `docs/design/decisions/` を作らない
- 設計と実装を同一レスポンスで一気に進めない
